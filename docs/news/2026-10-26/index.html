  1. 事件

    Wiz 从 9/15 起追踪一个名为 Gheist 的攻击（API 请求的 User-Agent 就是 gheist）：攻击者拿泄露的 GitHub token，对 token 能访问的每个仓库建一个 ci-sync-加六位随机字符 的分支，提交 .github/workflows/sync-check.yml（提交信息为 ci: sync config），push 触发后把 env 和 toJSON(secrets) 用 base32 编码打印到日志，通过 GitHub API 下载日志后几秒内删除运行记录。三个关键点：GitHub 只遮蔽原样出现的 secret，base32 后就不遮蔽了；permissions: {} 只限制 GITHUB_TOKEN，不限制 secrets 上下文；有部署环境的仓库会用 matrix 把环境级（往往是生产）secret 一起打出来。10/19 起变种还加了一个只投给自托管 runner 的 sync-host 任务，搜索 31 种 token 格式（含 Anthropic、Hugging Face 等 AI 厂商 key）、/proc/*/environ、Docker socket 和云元数据。GitHub 自 7/28 起会把公开仓库的可疑 workflow 挂起等待审批，所以公开仓库的运行都停在 action_required；但私有仓库和 GitHub Enterprise Server 不受这个保护，Wiz 看到了攻击成功、随后用同一组织的云凭证枚举 AWS Secrets Manager 的案例。

    为什么值得关注

    这类攻击不需要任何外部域名，secret 是通过 GitHub 自己的 API 流出去的，网络出口拦截完全无效。很多团队现在给 coding agent 和自动化账号发长期 PAT，这些 token 一旦被信息窃取木马拿到，就能按同样手法把 CI 里的数据库密码、支付渠道密钥、云角色一次性带走。Wiz 给出的猎杀指标非常具体，今天就能查。

    工作中怎么用

    1）在所有组织里搜 ^ci-sync-[0-9a-z]{6}$ 分支和只新增 sync-check.yml 的提交，在审计日志里找 gheist UA 和完成后一分钟内被删除的运行；2）用 OIDC 登云的话，去 CloudTrail 查 subject 里带 ci-sync- 的AssumeRole 记录，这一条不依赖 GitHub 日志；3）加固：生产环境 secret 必须走带审批人的 environment，OIDC 信任策略只认受保护分支，给 agent 和机器人换成 GitHub App 或短期 fine-grained token，自托管 runner 改成一次性主机、不挂 Docker socket。中招的话要轮换该仓库可见的所有 secret，删分支不等于撤销泄露。

  2. 事件

    modelcontextprotocol/servers 在 10/25 早上（北京时间 08:03）发布 v2.1.0。server-filesystem 2.0.1 修了四个问题：检查和写入之间父目录被换成符号链接就能写到允许目录外（Linux/macOS 已修，Windows 只部分修复）；访问检查会去掉末尾引号或空白但实际操作不去，导致同名加后缀的兄弟目录可被访问；大小写不同的符号链接在 macOS 这类不区分大小写的卷上能绕过检查（2026.8.31 引入的回归）；list_directory_with_sizes 会泄露允许目录外文件的大小和时间。server-everything 2.0.1 的 HTTP/SSE 传输不再返回 Access-Control-Allow-Origin: *，并校验 Origin，之前用户浏览的任意网页都能调用它的 get-env 等工具。mcp-server-fetch 2026.10.24 修了 IDNA 主机名检查和连接用的不是同一形式、NAT64 地址包着内网 IPv4 没被拒绝、重定向后不再检查 robots.txt 三个问题。

    为什么值得关注

    这几个参考服务器是很多人第一个装的 MCP，也常被拿来当自写服务器的模板。这次修的都是“检查时的值和使用时的值不一致”这一类问题（TOCTOU、规范化不一致、主机名两种形式），自己写文件类、抓取类 MCP 工具时最容易犯同样的错。还有一个坑：TypeScript 服务器从日期版本改成了语义化版本，包管理器认为 2.0.1 比 2026.x 旧，不会主动提示升级。

    工作中怎么用

    1）盘点团队和 Claude Desktop、IDE 配置里用到的 server-filesystem、server-everything、mcp-server-fetch，显式安装 @2.0.1 或 2026.10.24（例如 npm install @modelcontextprotocol/server-filesystem@2.0.1）；2）任何本地开 HTTP 端口的 MCP 服务器都要校验 Origin、去掉通配 CORS；3）自研的 MCP 工具做一次自查：路径校验和实际打开用同一个规范化结果，最好用 openat/O_NOFOLLOW 一类方式；URL 抓取类工具在解析出 IP 后再判断内网地址，并把重定向后的每一跳重新校验。

  3. 事件

    Breunig 回顾了 2024 年“上下文越大越好”的思路带来的四种失败（上下文投毒、分心、混淆、冲突），并把应对手段归成六类：上下文增强（RAG、skills）、工具装载（按任务筛选工具，他见过一个企业每次启动给每个工程师装 600 个 skill）、上下文隔离（子 agent）、上下文修剪、上下文外置（写到文件或数据库）、上下文摘要（压缩）。他用 DSPy 展示这些在 harness 里各只需几行代码。2026 年的新问题有两个：一是“对抗权重”，模型过拟合训练时的工具和环境，比如 Claude Code 系统提示里反复要求并行调用工具；二是“上下文惯性”，Anthropic 的 Memento harness、微软的 Fork-and-Flush、伯克利的 Scaling Discovery Requires Forgetting 三方都发现，agent 跑久了会执着于一个子任务，解法都是定期写一份简短笔记然后清空对话、保留环境。他的建议很直接：上下文到 20 万 token 左右就该考虑重开。他预测 2027 年的难题是长期运行的个人 agent 里 skills 和记忆越积越乱，需要“有策略地遗忘”。

    为什么值得关注

    这是目前对 context engineering 和 harness engineering 关系讲得最清楚的一篇：同一件事，从手写提示到系统拼装上下文，再到把这些决策写进确定性代码。“上下文惯性”和三篇同期研究互相印证，给长任务 agent 的设计提供了一条可执行的规则：定期清空对话，产物落在环境里。

    工作中怎么用

    1）给团队内部的长任务 agent（批量代码迁移、对账排查等）加一个“检查点”：每隔固定时长或 token 数让 agent 写进度笔记到文件，然后新开会话读笔记继续；2）把工具和 skill 的加载改成按任务筛选，而不是全量注入；3）看到自家提示里出现大量重复和全大写的指令，先怀疑是在对抗模型的训练偏好，考虑换工具形态而不是加更多强调；4）定期清理 agent 的 skills 和记忆，合并冲突项。

  4. 事件

    slee-persis/GVS5H 提出“基于账本的零样本自编排”：一个模型的多个新实例分解问题，通过共享文件系统里的计划、笔记和当前解来协调。在最新 100 道 LiveCodeBench 难题上测了 11 个开源和闭源模型，固定后端下最多提升 25.6 个百分点。编排后的 Qwen3.8 Flash Next 达到 93.0% pass@1，高于 Fable 5 的 90.4%，成本约为后者的 9%；本地部署的 Qwen3.8-27B 从 66.8% 升到 92.4%。作者也承认不是所有模型都受益，有的持平甚至变差，转录分析把提升归因于任务分解和持久化上下文。代码 MIT，论文和数据 CC BY 4.0。

    为什么值得关注

    这和上一条的“上下文外置、定期换新实例”是同一个思路，只是用在了成本上：把组织工作交给 harness，便宜的开源模型也能接近前沿模型。不过 HN 评论里有不少硬质疑：LiveCodeBench 已经接近饱和、没和 Astra、Opus 5.5 等最新模型比、给单次作答的基准加上了多轮修复和委派等于改了规则，耗时也可能是 10 倍。适合当方法参考，不适合当结论引用。

    工作中怎么用

    如果团队有本地部署模型的需求（数据不出域的代码生成、内部工具开发），可以照着它的“计划/笔记/当前解”三文件结构，在自家 harness 里做一个小实验：同一个本地模型多开几个新会话接力，对比单次调用的通过率、耗时和成本。评估时用自己的真实任务，不要只看 LiveCodeBench。

  5. 事件

    Microsoft Research 开源了 Agensh，目标是解决“总调度 agent 成为瓶颈”的问题。每个 worker 运行同样的五步循环：读目标和同伴进度、发 CLAIM 认领子任务（冲突用私信协商）、本地执行并尽早发现、按验收标准自检、合并到共享仓库后再循环。底层用三个服务连接：Gitea 托管共享仓库，Mattermost 做频道和私信，一个共享上下文板存 OBSERVED、FACT、FAIL、CLAIM、PATCH_SUMMARY 等类型化笔记。这套循环写在提示里而不是运行时代码里，底层单 agent harness 实验用的是 GitHub Copilot CLI，论文说也能接 Claude Code。在 ProgramBench 最难的五个任务（FFmpeg、gromacs、pandoc、PHP-src、ctags，从行为重建程序，离线 6 小时）上，GPT-5.6-sol 的平均通过率从 1 个 agent 的 19.31% 涨到 128 个的 28.78%；README 里补充的 GPT-6.1-sol 在 pandoc 上 32 个 agent 达到 79.59%。

    为什么值得关注

    这是少有的把多 agent 规模做到上千、并公开复现脚本的工作。它的结论也很实在：1 到 8 个 agent 只多了 1.37 分，规模收益要到几十上百个才明显；随着规模扩大，评审、集成这些角色是自发出现的，没有写死。对正在考虑“要不要上 agent 团队”的人，是一份有数据的参考。

    工作中怎么用

    可以借用它的两个低成本设计，而不必上千个 agent：一是用类型化笔记板（事实、失败、认领、补丁摘要）代替 agent 之间的自由聊天，方便事后审计；二是把协作协议写在提示里、用 Git 分支和 PR 作为唯一的合并通道，这和团队现有的代码评审流程天然兼容。想复现的话仓库里有 REPRODUCE.md 和 Docker Compose 配置。

  6. 事件

    winnin/farol 是一个 MIT 开源的 CLI 和 GitHub Action（npx @winninjs/farol 或 winnin/farol/action）。它不替代 AI 评审，而是在之后给批准人一份分诊报告：用 TypeScript 类型检查器、go/types、Python ast 分别在 base 和 head 上建声明图，列出改动会触达的所有现有页面、API、RPC、定时任务和脚本以及调用链；根据影响面、diff 覆盖率、安全发现、接口契约破坏和依赖变更给出“快速通过 / 简单评审 / 仔细评审”三档结论和风险分；能识别 GraphQL、FastAPI、Go handler、gRPC 的字段删除、必填参数新增、类型变化，并列出调用方服务。每次 push 生成全量和增量两份报告，不执行代码、不外传代码、不阻塞合并。

    为什么值得关注

    agent 写代码、agent 评审之后，人的批准成了最稀缺的环节。Farol 的思路是“确定性的部分交给代码、概率性的部分交给模型”，和第三条 Breunig 的结论一致：一行改到共享组件就挂掉 40 个页面，正是 AI 逐行评审最容易漏的情况。

    工作中怎么用

    目前只支持 TS、Go、Python，Java 服务用不了，但思路可以直接借：在支付或核心交易仓库的 CI 里，加一步基于编译器或 jdeps/ArchUnit 的影响面分析，把“这次改动触达哪些对外接口、哪些下游调用方”写进 PR 评论，再按影响面决定需要几个人审、是否需要回归测试。前端或 Go/Python 的辅助服务可以直接装它试试。

  7. 事件

    inside.java 10/25 宣布 JEP 544（Ahead-of-Time Code Compilation，负责人 John Rose）定为 JDK 28 目标特性。做法是在训练运行里把应用代码编译成本地代码并存进 AOT 缓存，生产运行一启动就能用上；如果生产负载和训练时不同，HotSpot 照常反优化、再由 JIT 生成新代码，AOT 和 JIT 代码在同一次运行里自动切换。设计目标包括：不改应用、库和框架代码；除了启用 AOT 缓存外不需要额外配置；支持 Serial、Parallel、G1、Shenandoah、ZGC；沿用现有的 AOT 缓存创建流程。限制是不做纯 AOT 模式、不支持交叉编译（训练和生产必须是同样的 CPU 架构和特性），首批只支持 AArch64 和 x64。它建立在 JEP 483（AOT 类加载链接）和 JEP 515（AOT 方法画像）之上。

    为什么值得关注

    Java 服务冷启动和预热慢，一直是扩容、发布和 Serverless 场景的痛点，以前要么上 GraalVM native image 牺牲动态性，要么靠 CRaC。JEP 544 在不改代码的前提下把“启动就接近峰值性能”带进了标准 HotSpot，对流量突增时需要快速扩容的支付、交易服务尤其有用。

    工作中怎么用

    JDK 28 预计明年 3 月发布，现在可以先做准备：1）在 JDK 25 上把 AOT 缓存（JEP 483/515）用起来，摸清训练运行怎么做、缓存放进镜像的流程；2）注意“训练和生产 CPU 特性必须一致”，混合机型的集群要按机型分别生成缓存；3）等 JDK 28 EA 带上这个特性后，挑一个核心服务对比首个请求延迟和达到稳定 P99 的时间。

  8. 事件

    版主 Wolvereness 10/24 晚发帖《Your tokens aren't valuable: No more AI》，规定：项目必须满一年且持续维护、有约三名以上贡献者和已有社区、不能是常见毕设类项目、不能是为 AI 做的（举例 MCP）；账号需满一年；明显用了 AI 的项目不收；不会英语的请去别的社区，理由是分不清 AI 写的和 AI 翻译的；发布 LLM 输出的会被永久封禁。版主承认“明显用了 AI”没有客观标准，规则就是为了给版主足够裁量权删“垃圾内容”。The Verge 10/25 跟进报道，评论区反复拿 Linux 内核举例：内核几天前刚取消了披露 AI 使用的要求，Linus 说“不会定那种‘不许用工具做 X’的蠢规则”。

    为什么值得关注

    这是开源社区对“AI 生成项目泛滥”最激进的一次反应，和 Linux 内核的立场正好相反。它说明两件事：一是 AI 辅助项目在社区里的信任成本在上升；二是“用了 AI”这个边界已经很难划，代码补全、翻译、无障碍字幕都算不算，规则只能靠人工裁量。

    工作中怎么用

    如果团队打算开源内部工具或 MCP 服务器，推广渠道不要依赖这类综合社区，转向 GitHub、HN、专门的 MCP 社区；同时把项目做得经得起审视：有测试、有真实使用场景、有不止一个维护者，README 里坦白哪些部分用了 AI 辅助。这也是给内部代码评审定 AI 使用规则时的一个反面参考：按产出质量把关，比按“是否用了 AI”一刀切更可执行。

  9. 事件

    Max Woolf 列出了从 6 月 GPT-5.6 到 9 月底 GPT-6.1 Sol、Claude Opus 5.5 的价格变化：例如 GPT-5.6 Luna 7 月降价 80%，Fable 5.1 把缓存读取价格降了 75%，Opus 5.5 比 Opus 5 整体便宜 40%–60%，GPT-6.1 Sol 把缓存读价格减半到输入价的 5%。他强调，coding agent 每一轮都要读完整的历史缓存，缓存读取占总 token 支出的 96%–99%，命中率通常 90%–100%，所以缓存读价格才是真正决定成本的因素。Vercel 网关数据显示每 token 成本降到 4 月的 43.3%，但总支出在涨，因为模型变好的速度比变便宜还快。他的解释是：在 harness 里切模型几乎没有成本，DeepSeek V4.1 Flash 在 OpenRouter 上有 29 家推理商，Kimi K3.1 Pro 以一半价格逼近 Opus 5.5，所以“现在是亏本补贴、以后会涨价”的说法站不住。

    为什么值得关注

    很多团队做 agent 预算时还在只看输入输出单价。这篇把“缓存读取价格和命中率”摆到了成本中心，并给出了一个有争议但有数据的判断：价格大概率继续降，而不是以后涨回来。评论区对补贴论和长期定价分歧很大，值得一看。

    工作中怎么用

    1）重算团队 coding agent 的成本模型：拿实际账单拆出缓存读、缓存写、输入、输出四项占比，选模型时按“有效输入成本”比较；2）提示和工具定义尽量保持前缀稳定，提高缓存命中率，这比换便宜模型更直接；3）对数据不出域的场景，评估 OpenRouter 或自建推理上的开源权重模型，作为主力模型的低成本备选。
