  1. 事件

    Dragos 首席研究官 HD Moore 在 7 月到 11 月间，向常用 AI 服务发送了约 200 万条 prompt，每条只埋一个独一无二的秘密（空 AWS 账号的真实 access key、SSH 密码、唯一 URL/DNS 名、私有 git 仓库地址），再看这些秘密在哪里被使用。结论有三条：① 至少 3 家推理托管商被入侵，其中最大一起里约两百把 AWS key 被盗，连「模型还没跑就被拒绝的请求」也被抄走，说明攻击者在服务入口处复制请求；另两起里被偷的请求有的带 ZDR 标记；拿到 key 的人几小时内就开始列 S3、翻 Secrets Manager/Parameter Store、尝试开通 Bedrock、加自己的 IAM 用户，诱饵 key 一共被调用了数万次 AWS API。② 推理市场上的个别转售商只靠「最低价挂单 + 打开请求日志」就拿到了别人的 prompt。③ 一家中国 AI 实验室的系统抓取了发给它模型的过半数秘密 URL，其中约三分之二的请求标了「不收集数据」或 ZDR；通过美国托管商转售的同一模型也触发了同一个爬虫。11/21（窗口内）有 HN 用户贴出 OpenRouter 的通知邮件：研究者埋在 MiniMax 模型请求里的 URL 在 40–130 小时后被第三方访问，不论请求是 MiniMax 直连还是经 AtlasCloud、Novita、StreamLake 转发；OpenRouter 说问题出在 MiniMax 及转发方，已暂时移除这些端点的 Zero Data Retention 标签。Ars Technica 11/21 也更新了这一进展。

    为什么值得关注

    大家的 agent / coding agent 正在把整段代码、日志、配置、工单塞进上下文，里面经常混着 token 和内部 URL。这份研究第一次用可追踪的证据说明：路由层（OpenRouter、Vercel 等）后面的每一跳都会解密 prompt，ZDR 只是一个「请对方遵守」的标记，攻击者已在服务商内部时它不起作用。对支付、金融类团队来说，这直接关系到数据出境和合规承诺。

    工作中怎么用

    1）给 agent 加「出站前脱敏」：在调用模型前用 secret scanner 过滤 key/token/内网 URL，Context Engineering 里把「什么能进上下文」写成规则；2）在路由层显式锁定上游 provider，不要用默认的低价 provider 池；敏感仓库只走一手厂商或自托管；3）自己也埋金丝雀：用 Canarytokens 之类的工具在测试 prompt 里放诱饵 key/URL，定期检查有没有被触发；4）若用过 OpenRouter 上的 MiniMax 端点，查收通知邮件，按已泄露处理相关请求里出现过的凭据。

  2. 事件

    Cline CLI v3.0.75 发布说明：一次性运行「因为没人在键盘前审批工具」改为默认 yolo 模式而不是 act 模式；关掉 auto-approve（--auto-approve false 或保存的设置）、显式传模式参数、保存了 plan 模式或使用 /team prompt 时仍保持 act 模式；yolo 模式没有 team 工具，需要时要传 --act。同版本还有：--timeout 和 Ctrl+C 终于能打断一次性运行的第一轮；CLI 不再读取启动目录下的 .env 和 bunfig.toml；read_files 结果不再截到 8k 字符，改为工具上限（2000 行或约 48k 字符）；删除了会把完整请求体写到磁盘的 CLINE_CAPTURE_* 调试变量；实验性 CLINE_CLOUD_SESSIONS=1 可以从 TUI 把任务丢到 Cline Cloud。扩展 v4.1.27 的 MCP 面板会给服务端声明为只读的工具显示「read-only」标记。Qwen Code v0.28.3 则把 GitHub 加为第三个托管渠道适配器（另有实验性企业微信适配器）、新增只发送的通用 Webhook 渠道，Hosted Harness 会在工作结束后挂起空闲托管会话、下次请求时再冷启动，也可以选择在一轮内跳过因容量报错而耗尽的模型。

    为什么值得关注

    「谁在审批工具调用」是 harness 设计的核心问题。Cline 的理由很直接——一次性运行没人能点同意，于是默认放开；但这意味着现有 CI 脚本、git hook 里调用 `cline "..."` 的地方，升级后权限悄悄变宽。另外几条（不读启动目录的 .env、删掉落盘请求体的调试变量、MCP 只读标记）则是在收紧攻击面，正好和上一条的供应链研究呼应。Qwen Code 的托管渠道 + 空闲挂起，代表 agent 正在变成常驻服务而不是终端里的会话。

    工作中怎么用

    1）全局搜一下 CI/脚本里的 cline 调用，升级前决定是保持 yolo 还是显式加 `--auto-approve false` / `--act`，并确保它只跑在隔离容器里；2）自家 MCP server 给只读工具标上 readOnly 注解，客户端已经开始利用这个信号做审批分级；3）做常驻 agent 时参考 Qwen Code 的「空闲挂起 + 冷启动」，按会话活跃度控制资源，而不是一直占着进程。

  3. 事件

    SimpleBench（200 多道多选题，测时空推理、社交常识和「语言陷阱题」，人类基线 83.7%）在 11/18 收录了 OpenAI 的 6.2 代模型。榜单数据：GPT-6.2 Sol 69.9%（第 30），而 GPT-6.1 Sol 82.9%（第 10）；GPT-6.2 Astra 77.3%（第 17），GPT-6 Astra 83.6%（第 9）；GPT-6.2 Astra Pro 79.2%（第 16），GPT-6 Astra Pro 86.5%（第 8）。同期 Claude Fable 5.2 94.9% 第 1，Gemini 4 Neon 94.4% 第 2，Gemini 4 Carbon / Argon / Hydrogen 均在 91% 以上。HN 帖子 11/21 上榜，评论有人说 6.2 是 OpenAI「口碑最差的一次更新」、更懒；也有人认为 6.2 「太听指令」，灰色地带直接不处理；还有人质疑一个只测陷阱题的榜单能代表多少真实使用。

    为什么值得关注

    11/18 我们报过 GPT-6.2 发布，当时的卖点是价格和 agent 能力；这是第一个独立第三方榜单给出明显的反向信号。对把模型当 agent 大脑的团队来说，「新版本更便宜」不等于可以直接替换，回归尤其容易出现在边界和常识判断上，而这些恰恰是 agent 出事的地方。

    工作中怎么用

    1）模型升级前在自己的 eval 集上做 A/B（尤其是需要「质疑指令」「发现题目有坑」的用例），不要只看官方 benchmark；2）路由层先只把一小部分流量切到 6.2，对比任务完成率和返工率；3）把「明显矛盾的指令」类陷阱题加进 agent 回归测试，SimpleBench 的公开样题可以参考。

  4. 事件

    作者把 agent 跑在真实的 IBM PC 5160 上（演示用 86Box 模拟同一配置）：HARNESS.EXE 只有 176KB，自己拼 Messages API 请求、解析流式 SSE 和 JSON、执行工具、把每段对话按 API 原格式存在磁盘上；8088 唯一不做的是 TLS，交给另一台机器上的隧道（tunnel.py / socat / stunnel），API key 也可以只放在隧道上，不落到 PC 磁盘。18 个工具覆盖读写文件、搜索、运行 DOS 程序（单次最多 12 条命令，可要求截图）、读写内存和 I/O 端口、PC 喇叭放音乐，以及自己的笔记（C:\MEMORY）。编译时 harness 保存状态退出内存，让 Turbo C 拿到约 450K，编完再回到同一对话。系统提示和工具定义走 API 缓存，首轮之后每个工具结果上传约 500 字节；默认开「安全模式」，任何改文件/内存/端口的操作都要按 y 确认；CLAWDOS.LOG 记录每轮的首 token 时间、上传量、输入输出 token 和缓存命中。作者说除了说明框里那段话，仓库 100% 由 Claude 编写，代码约 13,000 行 C/C++。

    为什么值得关注

    现在很多 harness 动辄几百 MB 依赖，这个项目把 coding agent 拆到只剩必需件：一个 loop、一组带审批的工具、磁盘上的对话和记忆、缓存友好的请求结构、可观测日志。它也证明了 prompt caching 对慢链路和成本的作用，以及「密钥放在边界代理、不放在 agent 主机」这种设计是可行的。

    工作中怎么用

    1）拿它的工具表和 docs/API.md 做参照，检查自家 agent 的工具是否过多、哪些需要审批；2）照搬「密钥只在出口代理」的做法：让 agent 进程拿不到 API key，由网关注入；3）学它的单行 flight recorder，每轮记录 ttft、上传字节、cache read/write，用来定位 agent 慢和贵的原因。

  5. 事件

    SafeDep 分析了 npm 包 @leadstack/crm-connect：自称 LeadStack CRM 官方客户端，账号 zmaticoo 在 11/16 发布了 9 个版本。1.0.15 的 postinstall 安装 Nous Research 的开源 Hermes Agent 及其 Telegram 网关，从 72.62.1.108 拉取 .env（模型 key、Telegram bot token）和 SOUL.md（agent 的常驻指令，位于系统提示最前面），注册为 systemd 服务并改名为「LeadStack routing」，同时删掉原 Hermes unit 文件；npm install 以 root 运行时 agent 就是 root。1.0.18 改为装用户级服务并开启 linger，后续版本改为下载 JS 或二进制执行。SafeDep 在最后一个版本发布 5 分钟后标记，npm 已下架；但同一发布者 11/18 又发了三个包，tarball 里没有恶意代码，只声明一个指向攻击者服务器的可选依赖，内容可以随时替换。SafeDep 根据诱饵文案推断目标是外汇/差价合约经纪商的 CRM 和线索数据（未在受害者处观察到）。同类手法 9 月已出现在通过暴露的 Docker API 传播的 Carbonato 僵尸网络中。

    为什么值得关注

    这是「agent 即植入物」的典型案例：通用 agent 自带命令执行、文件读写、浏览器和定时任务，攻击者省掉了写远控的功夫，还能用自然语言下指令。SOUL.md 在线下发也意味着恶意行为不在包里，静态扫描只能看到「装了一个开源 agent」。金融/经纪类团队是明确目标。

    工作中怎么用

    1）CI 和服务器上禁止以 root 跑 npm install，默认 --ignore-scripts，只对白名单包开放 install script；2）出口流量告警：服务器长轮询 api.telegram.org、或无业务原因访问模型 API（文中是 api.moonshot.ai），都值得查；3）资产清单里加一项「主机上有没有 agent 运行时」（hermes、systemd 里的陌生 unit），把未登记的 agent 当后门处理；4）用 SafeDep 给出的 IoC 和 grep 命令扫一遍 lockfile。

  6. 事件

    GnuPG 11/20 发布 GPGME 2.3.1：用带超长 user id 的 OpenPGP 密钥可以触发双重释放（读取 gpg 状态行时重新分配缓冲区，提前返回导致上下文保存了已释放的旧指针），可以借此泄露数据，「不能排除 RCE」。受影响的包括 Gpg4win、GnuPG Desktop、大多数邮件客户端、Samba、Flatpak 等；漏洞由 GitLab 在 11/12 通报，原定 11/25 协调披露，因 Ruby2Shell 让 GitLab 提前更新而提前公开。HN 评论有人指出这是 double free 而不是现成的 RCE 链，也有人说 Red Hat 几年前就在自家包里修过但上游没合。另一边，pwn.ai 公开 Upload2Shell：Ghostscript Type 1 字体加载器的 use-after-free 能越过 -dSAFER 沙箱执行命令；他们确认了 Debian 13 CUPS（匿名 IPP 打印任务）、Roundcube（收件人看邮件即触发缩略图）、WordPress 插件 Forminator 和 Essential Addons for Elementor（未登录上传）、MediaWiki PdfHandler、Mayan EDMS 等利用链，Google 的文档渲染链路也被打到（11/10 已修）。修复版为 Ghostscript 10.08.0，Debian、Ubuntu 已有补丁包；页面还列出 Gradio、ERPNext、Paperless-ngx 等通过 Pillow 或直接调用把文件交给 Ghostscript 的路径。

    为什么值得关注

    支付和金融系统里大量存在「上传凭证/发票/KYC 材料 → 自动生成缩略图或转 PDF/A」的流程，以及「验签对账文件」的流程，这两类恰好分别对应 Ghostscript 和 GPGME。文件名是 .png 也可能被转给 Ghostscript；签名校验本身就会解析攻击者提供的密钥。连同本周的 Java4Shell、OpenSSL、Ruby2Shell，「默认路径上的解析器」是这一轮漏洞潮的共同点。

    工作中怎么用

    1）盘点镜像和主机里的 ghostscript、libgpgme 版本，分别升到 10.08.0 / 2.3.1，静态链接的二进制需要重新编译；2）上传链路里限制 ImageMagick/Pillow 可识别的格式（禁 PS/EPS/PDF 委托），渲染放进无网络的隔离 worker；3）对账、签名校验服务只接受预先登记的公钥，不解析对方随文件附带的任意密钥；4）把「哪些服务会调用外部解析器」做成资产清单，下次出漏洞时能当天定位。

  7. 事件

    MAS 局长 Chia Der Jiun 11/19 在新加坡金融科技节的主旨演讲中说，很多金融机构还没有为 agent 设定访问条款和通道，有些用户直接把账户登录信息交给 agent，银行无法判断它是否获得客户完整授权、是否在 mandate 内操作、出错由谁负责。MAS 总结 SAFR（Safeguards for Agentic Finance at Runtime）第一阶段的四条经验：有边界的自主权、明确 agent 的身份和授权、mandate 要具体（允许的动作、限额、条件）、控制强度和授权大小成正比。下一阶段将推动「know your agent」协议，在客户 agent 和金融机构之间交换四类信息：agent 是谁、代表谁；被授予什么权限；在什么 mandate 下运行；来源和可靠性有什么保证。金融机构据此确定给 agent 的条款和范围，并开设专用安全通道。另外 MAS 将与 Future of Finance Institute 建立 Agentic Money Sandbox，测试两个场景：企业 agent 监控流动性、决定资金调拨并用代币化存款执行；客户 agent 用代币化存款或稳定币付款，由银行/支付机构先核验身份与授权、执行风控。演讲没有给出沙盒启动时间。CryptoSlate 11/21 的解读指出「agent 出错或越权谁负责」仍未回答。

    为什么值得关注

    卡组织（Visa/Mastercard）解决的是「agent 拿什么付」，MAS 这次讲的是「银行凭什么接 agent 的指令」，而且明确把 mandate 和授权做成需要机器可读交换的字段——这本质上是一套 agent 授权的本体/数据模型。做支付和风控的团队，可以预期未来的接入规范会要求这些字段。

    工作中怎么用

    1）在自家支付/开放银行 API 里预留 agent 请求的元数据：agent 标识、委托人、授权范围、限额、mandate 引用、签发方，先记录再逐步用于风控；2）把「客户把网银密码交给 agent」当成需要识别和阻断的风险场景，而不是默认放行；3）关注 SAFR 文档（v1.1 PDF）里的运行时决策模型（拒绝/升级/自动执行/观察），可以直接借来设计内部 agent 的审批分级。
