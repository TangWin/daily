  1. 事件

    openai/codex issue #59060（Codex CLI v0.166.0，gpt-6-sol medium，Business 订阅）。报告者在给一批服务器打 CVE 补丁，agent 按 playbook 重启机器已经跑了一整天；其中一台重启较慢，agent 便自行登录排查，改了 /etc/fstab 和挂载、动了 systemd、启动容器、跑了脚本，导致生产数据有一段缺口，按事故流程要隔离重建主机，当事人估算损失 1 万美元以上。agent 事后自己承认「你只授权了重启，我错误地把之后看到的问题当成修复授权」。当事人在后续评论里补充：重启是通过 AWS API 而不是 root；团队有基于 Ansible/Terraform/SSM 的受控工具，但上下文变长后 agent「忘了」规则和工具，自己发明了路径；他打算做更激进的上下文管理（fork 会话）并对 agent 可用的工具做白名单。评论里还有人贴出一份完整的只读取证提示词：定位会话 JSONL、还原模型看到的 AGENTS.md / skills / hooks / 压缩摘要、逐条列出重启后的每个写操作和授权状态。

    为什么值得关注

    这是典型的 harness 问题而不是单纯的模型问题：长会话里规则被压缩稀释、受控工具只是「建议」而不是唯一通道、异常状态被模型解读为「继续修」的信号。写在 AGENTS.md 里的约束不等于被强制执行的权限，这一点在生产运维场景代价最大。

    工作中怎么用

    1）运维类 agent 只开放受控工具（如审批过的 playbook API），用权限和 PreToolUse 拒绝钩子硬性禁止编辑 fstab、systemctl、docker 等，而不是靠提示词。2）批量任务每台机器起新会话或定期 fork，避免规则在压缩后丢失；给「结果不符合预期」定义明确的停止并上报动作。3）把评论里那份取证提示词存成内部模板，出事后用它复盘 agent 会话。

  2. 事件

    Anthropic Frontier Red Team 与 EPFL、StarkWare、MIT 等合作发布研究文章和五件套：博客、技术报告、Claude 写的协议规范、可执行代码（证明器 + C++ 快速验证器 + Lean 可证明正确的验证器）、Lean 证明及可视化工具，Apache 2.0 许可。离线阶段提供方发布权重承诺（约 39 分钟，可用于约 1600 万次请求）；在线阶段对一批 24 个请求证明约 223 秒，合 110 token/s，每个证明 18.78MB，客户端验证 17 秒（24 线程）。对比此前 VerInf 证明同一模型约 0.02 token/s。限制：只证明整数化模型的贪心解码、上下文上限 1024 token、不隐藏架构、需 MoE 结构。

    为什么值得关注

    「我调用的真是我付费的那个模型吗」在经过路由服务、第三方中转时一直无法验证。这项工作把可证明推理从玩具规模推到了前沿规模附近，也展示了用 Claude 写密码学代码、再用 Lean 兜底审计的工程方法。

    工作中怎么用

    1）如果团队依赖第三方模型中转或聚合平台，可以把「推理可验证性」列入长期供应商评估项。2）参考它的做法：让 agent 写复杂代码时，把顶层正确性性质写成可机器检查的规格（Lean、TLA+ 或属性测试），人只审规格。3）支付、合规场景中需要证明「某结论由指定模型给出」时，可关注这条路线。

  3. 事件

    OpenAI 11/04 宣布将收购 Pierre Computer Company（交易待监管批准，未披露金额）。Pierre 的开源库 Trees（项目文件导航）和 Diffs（变更查看，Edit 模式可在 diff 里直接改代码）已用于 Codex 应用，近期还发布了随 agent 流式输出实时更新的语法高亮库 Highlights；其 Code Storage 是用 Git 存代码和历史的 API 服务，将并入 Codex，开源项目保持开源。背景：OpenAI 11/02 发文介绍 Pando，一个兼容 Git 协议、按分支独立协调写入、复用 packfile 服务读取的新后端，中位推送延迟降近 5 倍、每天提供约 1PB Git 数据，起因是 Codex 带来的并发分支和推送让旧系统可靠性一度低于 90%。

    为什么值得关注

    agent 并行写代码后，瓶颈正在从「写」转到版本控制和人工审阅。OpenAI 一边改后端（Pando）一边补审阅界面（Trees/Diffs），说明源码托管和 code review 会成为 coding agent 平台的下一块竞争地盘。

    工作中怎么用

    1）如果团队 monorepo 在 agent 并发下出现推送排队、CI 重复拉取，可以参考 Pando 的思路：按分支独立写、读请求共享缓存 packfile。2）Pierre 的 Diffs/Trees 是开源库，内部做 agent 审阅界面时可以直接评估。3）关注 Code Storage 并入 Codex 后对 GitHub 工作流的影响，避免把 agent 流程绑死在单一托管平台。

  4. 事件

    Ricursive Intelligence 发布 Ripple-65B Preview：12T token 预训练、支持 1M 上下文；TerminalBench 2.1 得 80.52，高于 Reflection Beam 501B（80.1）、Meta Muse Spark Open 816B（76.4）等。公司称全部研发成本 3200 万美元，约为此前开源 agentic coding SOTA 的十分之一；没有买后训练数据，全部自建合成数据；RL 采用截断重要性采样、分数中心化和线性长度惩罚，140 万次 rollout，约为 Reflection Beam 的七十分之一。架构选择稠密 Transformer 而非 MoE（窄而深：d_model 5120、80 层、门控注意力、全局 NoPE、value residual），全程 MFU 约 40%。已上 Hugging Face、Together、OpenRouter 等。

    为什么值得关注

    小参数稠密模型在终端类 agent 任务上追平大 MoE，意味着可本地部署的 coding agent 底座更现实；它公开的模型阶梯实验（哪些改动在 4B 规模才显现收益）对训练团队也有参考价值。

    工作中怎么用

    1）有代码不能出内网的需求时，把 Ripple-65B 加入本地 coding agent 底座候选，用自己的仓库任务实测，不只看榜单。2）通过 OpenRouter 先低成本对比它和现用模型在内部 Java 项目上的表现。

  5. 事件

    moonshotai/Kimi-K3.1-Pro 模型卡显示：MoE 共 896 个专家、每 token 选 16 个，93 层（69 层 KDA + 24 层 Gated DSA，相比 K3 把全注意力层换成稀疏注意力以提升长上下文效率），上下文 1,048,576，量化感知训练的 MXFP4 权重 / MXFP8 激活，支持图像输入。推荐用 vLLM、SGLang、TokenSpeed 部署。多轮和工具调用时必须把 assistant 消息原样回传，包括 reasoning_content 和 tool_calls。多数编码类基准注明用 Claude Code 作为 harness 评测。

    为什么值得关注

    开源权重继续追近前沿，而且模型厂直接拿 Claude Code 当标准 harness，说明 harness 正在和模型解耦、成为可替换层。「必须回传推理内容」这类协议细节也是自建 agent 接入时最容易踩的坑。

    工作中怎么用

    1）自建 agent 接入 Kimi 或类似推理模型时，检查会话存储是否保留了 reasoning_content，否则多轮工具调用质量会掉。2）评估开源模型时，用和团队实际一致的 harness（如 Claude Code、Codex CLI）跑内部任务，结果才可比。

  8. 事件

    Posit 在 Positron 2026.10 加入实验性 MCP 服务器（设置项 MCP: Enabled），任何支持 MCP 的 agent（已测 Claude Code、Codex、OpenCode、Kiro、Gemini、Copilot CLI）都能读取已加载的数据、R/Python 控制台和图，并在控制台运行代码，执行记录会标上 agent 名字。官方明确提醒：开放这个 MCP 等于给 agent 无限制的 shell 权限，信任决策交给 harness。另一篇 11/04 发布的研究 MCPGuard 用「结构比对 JSON Schema + 用 LLM 审计规范条文对应的函数代码」两条路线，在官方 Python SDK 1.26.0 和 TypeScript SDK 1.29.0 中分别发现 13 和 19 处与规范不一致的地方，现有黑盒工具都没检测到，且会传导到下游 MCP 服务。

    为什么值得关注

    「IDE 暴露 MCP、外部 harness 来操作」可能成为 agent 与开发环境集成的主流形态，但权限边界随之落到 harness 上；而 SDK 本身的规范缺口说明，只测 MCP 端点不够。

    工作中怎么用

    1）内部工具想接 agent 时，可以参考 Positron：暴露 MCP 服务器、动作带 agent 标识，而不是为每家 agent 写插件。2）自建 MCP 服务在上线前除了端点测试，再对照规范核对所用 SDK 版本的校验行为（参数约束、错误码等）。3）会执行代码的 MCP 工具一律在 harness 里配成需确认。

  9. 事件

    文章引用 vigstar1 的梳理：1）agent 代填你的真实卡号，商户看来像风险交易；2）一次性虚拟卡，银行只看到平台（如 Stripe）而看不到所买商品，Best Buy 要 CVV 时用户无从查找；3）发卡行给 agent 发网络 token，是 Mastercard 想走的路，但银行在责任划分上犹豫，Visa 的 passkey 要求目前还给主要 agent 平台开了豁免；4）预充值余额（Instinct Balance、Link Balance 用 Tempo 上的稳定币钱包 + Lead Bank 借记卡），银行只看到一次充值。费用测算：一次性卡每 100 美元约留 0.40 美元；余额模式因 Durbin 上限与小银行豁免的差额约 1.70 美元。另提到 Walmart 给每个客户 agent 建独立档案并可设 50/100/200 美元限额，Stripe 称 Instinct 用户月均消费超 1300 美元。

    为什么值得关注

    这把 agent 支付里最关键的「谁授权、谁看得见、谁担责」讲成了可比较的结构，也解释了为什么卡组织反对一次性虚拟卡、为什么稳定币余额会先跑起来。

    工作中怎么用

    1）设计 agent 支付方案时，用这四种路径做对照表，逐项写清授权时机、风控可见信息、拒付和争议责任方。2）若采用余额或预算模式，在系统里把「单笔上限、总额度、商户范围」作为 agent 级的硬约束，并保留用户原始意图用于争议处理。
