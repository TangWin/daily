  1. 事件

    Anthropic 工程博客（Addy Osmani 等）公开 Claude Code 团队的审查流程：6 月到 9 月合并 PR 数翻倍以上，回滚占比下降超过 40%。做法是分层检查：提 PR 前让 agent 跑测试、构建、截图证明结果，再用全新上下文的子 agent 审 diff；CLAUDE.md 写项目约定，REVIEW.md 由代码负责人写“这块代码出错长什么样”；把历史事故 PR 做成评测集，每天跑审查器；审查最多 3 轮，之后只审新增 diff，避免 agent 互相“刷轮次”（曾有 PR 一夜跑了 50 多轮）。计费、自动更新、CI 这类高风险代码始终要人审。

    为什么值得关注

    这是目前最完整的“agent 写代码时代怎么审”的一线实践，指标（人工审批数、等待时长）和护栏（回滚率、事故率）都给得很具体。

    工作中怎么用

    可以直接照抄落地清单：PR 模板加“测试 / 风险 / 如何回滚”三栏；先在一个仓库接 AI 审查器并调 REVIEW.md；用 CODEOWNERS 把支付、鉴权、发布流程锁死必须人审；把过去的线上事故整理成审查器的评测集。

  2. 事件

    The Register 报道：PostgreSQL 19 从原定的 9 月底/10 月初推迟到 11 月 19 日左右，8 到 10 个重要特性被回退到 PG 20，其中包括 SQL/PGQ 图查询。核心提交者 Peter Eisentraut 说，部分原因是 LLM 辅助审查在发布前几个月变强，翻出一长串边界问题，每个修复不大，但处理开销累积起来时间就不够了。他强调这和“vibe coding”无关。

    为什么值得关注

    这是一个反直觉的信号：AI 审查让成熟项目的质量门槛突然抬高，短期反而拖慢交付。和上一条 Anthropic 的“审查要收敛”正好互相印证。

    工作中怎么用

    引入 AI 审查时，别在发版前夕对老代码一次性全量扫；给 AI 发现的问题分级，并预留修复预算，否则发布节奏会被打乱。

  3. 事件

    Anthropic 前沿红队发文：员工让内部研究模型在不给线索的情况下研究 NIST P-192/224/256/384/521 曲线种子的来历，模型不到半小时就发现它们不是任何哈希，而是 C 库随机数生成器用 Unix 时间戳初始化后的输出（P-256 是第 1842 个候选）。Filippo Valsorda 用 Go 独立复现并确认，三年前设立的悬赏被领取，奖金捐给了运营 Let's Encrypt 的 ISRG。

    为什么值得关注

    一方面，这排除了 ECDSA 曲线被埋后门的长期猜疑；另一方面，它展示了模型“推测当年软件怎么写的再反推”的研究能力，这类开放问题以前要靠人花几年。

    工作中怎么用

    支付和签名系统里用 P-256 的不需要任何改动，可以当作给安全评审的一份定心材料。另外可以借鉴它的思路：让 agent 先假设“生成过程”，再用可验证的程序去对答案。

  4. 事件

    推理云 Neuralwatt 分析一个月流量：各客户端未命中缓存的输入占 1.6% 到 11.1%，缓存一旦失效，请求能耗约翻倍。实验发现所有缓存失效都来自 harness 改动了已经发出的内容：OpenCode 1.x 的计划模式提醒、omp 替换重复读取的文件、把日期写进系统提示、按字母序把新 MCP 工具插进工具列表中间、在提示开头写推理强度。改工具列表或推理强度的轮次缓存失效概率高出 20 倍以上。

    为什么值得关注

    这是少见的、按真实流量量化“上下文怎么拼”对成本影响的数据，而且给出了具体哪些写法会坏事。

    工作中怎么用

    自研 agent 时坚持“只追加不改写”：日期固定在会话开始时，新工具和技能追加到末尾，压缩时保留前缀。接入 MCP 的服务端可以把“提示首个差异位置”作为监控指标。

  5. 事件

    官方 MCP Java SDK 同日发布 v2.1.0、v2.2.0-M1 以及 1.1.5/0.18.5 维护版。2.1.0 新增工具列表过滤，基于 HttpClient 的传输改成 Publisher 风格，加入 Streamable HTTP 会话清理和保活，修复 STDIO 线程安全和 LAST_EVENT_ID 恢复时的流泄漏，并移除了 2024-11-05 协议。2.2.0-M1 新增 io.modelcontextprotocol.modern 无状态服务端，通过了 37 个 2026-07-28 必测场景：没有会话，适合水平扩展；同步异步一套 API；工具、资源、提示词来自你自己实现的仓库，方便做按租户过滤和分页。

    为什么值得关注

    Java 后端接 MCP 最大的痛点是有状态会话难以水平扩展，这次官方给出了无状态方案；按租户提供工具目录也正是企业场景需要的。

    工作中怎么用

    现有服务先升级到 2.1.0 或 1.1.5，拿到会话清理和泄漏修复。新的多租户 MCP 服务可以拿 2.2.0-M1 做技术验证，但它是里程碑版，客户端和 tasks 还不支持，暂时不要上生产。

  6. 事件

    Red Hat Connectivity Link 1.5 中的 MCP 网关正式发布。支持独立或共享网关的团队隔离；联合上游服务的 prompts 和 resources，并能按 JWT 声明过滤；通过 discover_tools / select_tools 两个元工具做渐进式工具发现，避免一次性把全部工具塞进上下文；同一个 /mcp 端点同时支持 2025 系列协议和 2026-07-28 无状态协议；每次 tools/call 都写结构化审计日志。

    为什么值得关注

    昨天 Stack Overflow 说 MCP 缺生产配套，今天就有大厂交出网关方案，可以当作“MCP 网关应该有哪些能力”的参考清单。

    工作中怎么用

    自己做 MCP 网关时可以对照它的功能：按团队隔离、按权限过滤工具、渐进发现、审计日志。即使不用 OpenShift，上游开源项目 Kuadrant 也可以参考。

  8. 事件

    Mercor 发布“基准地图”：把 29 个 AI 基准的题目映射到美国劳工部 O*NET 的 18,797 项任务，只有 208 种职业有任务被至少 5 道题覆盖，22 个职业大类中有 6 个完全没有。结论是美国 90% 的工作时长花在基准几乎没测过的任务上，而且基准偏向高薪大职业，比如律师被测得很多，法律秘书和书记员几乎没有。

    为什么值得关注

    这直接质疑了“基准分数代表 AI 能干多少活”的说法。HN 上争论很多，包括 Mercor 本身是卖评测数据的，存在利益相关。

    工作中怎么用

    评估 agent 能不能接手某类业务时，别只看公开基准，要用自己的真实任务做小评测集，比如支付对账、工单分类这类长尾工作。

  9. 事件

    一位在西班牙语地区的用户在 Anthropic 控制台充值时输入 5.04，结果被扣 504 美元（加增值税共 569.52 美元），称没有二次确认页，客服机器人也拒绝退款。评论区有人指出页面其实会显示“应付总额 $504.00”，也有人认为原帖像 AI 写的。不管谁对，小数点和千分位的本地化解析导致金额错误，是支付系统的经典问题。

    为什么值得关注

    这是一个现成的支付 UX 反面案例：区域格式、金额校验、确认步骤、自动客服的退款边界，每一环都可能出事。

    工作中怎么用

    可以拿来检查自己的充值和支付页：金额输入是否按区域明确解析，遇到歧义是否直接拒绝；金额超过常用值时是否二次确认；客服机器人遇到“系统缺陷导致多扣”是否必须转人工。

  10. 事件

    （补报，10/15 晚发布）Wix 的多 agent 平台 Symphony 接入 Stripe 的 Link 钱包。agent 发起采购或付款请求，店主在 Link 应用里批准具体金额，Stripe 再签发一次性支付凭证或虚拟卡，agent 全程看不到真实卡号。目前每笔都要批准，Stripe 的路线图是之后改成“批一次预算，预算内自动付”。先向美国用户开放，只支持美元。

    为什么值得关注

    这是 agent 支付在真实中小商户场景的落地样本：先逐笔授权，再到预算授权，凭证只对单笔有效，体现了现在主流的风控思路。

    工作中怎么用

    设计 agent 代付时可以照这个分层：先逐笔批准，后放开预算；用单次凭证或虚拟卡隔离真实支付工具；批准请求设超时（Wix 用 10 分钟窗口）；同时做幂等，防止重复扣款。
