  1. 事件

    State of AI 转述彭博报道（文章 11 月 2 日，HN 11 月 8 日约 562 分、338 评论）：高盛 10 月更新内部指引，Anthropic 的 Claude Code 和微软的 GitHub 只开放给工程师，横跨交易、量化和软件的 strats 保留权限，大多数交易员和银行家被切断。他们原本用这些工具盯客户交易流、给市场走势和头寸建模、做材料。7 月 CIO Marco Argenti 还在夸非技术员工的「vibe coding」；高盛约 4.7 万员工里工程师超过 1.2 万。限制只针对能自己写代码、跑代码的第三方 agent，内部多模型 AI 助手照常可用；高盛 4 月已在香港下架 Claude，同时它和摩根士丹利是 Anthropic IPO 的主承销商。文章对比了巴克莱：10 月称年底一半开发者用 Claude Code，三周后裁员 5000 人里包括开发者。

    为什么值得关注

    这是头部投行第一次按「角色」而不是按地域或合同收回 coding agent，理由落在三件事：信息隔离墙、没人审的 agent 代码进了日常使用、按 token 计费的成本。HN 评论把它归结为 Simon Willison 说的致命三件套（私有数据 + 不可信输入 + 外传能力），对任何在受监管业务（包括支付）里推 agent 的团队都是现成的反面教材。

    工作中怎么用

    在支付或金融团队推 coding agent 前，先定三条：非工程人员用 agent 写的工具必须有一位具名工程师认领才能碰生产数据；信息隔离、数据权限和软件准入规则同样适用于 prompt 生成的代码；agent 不和客户数据、交易数据共用同一台机器或同一身份，放进隔离沙箱。收回权限时记录大家拿它做了什么，转成工程需求。

  2. 事件

    Caleb 的博文（9 月 21 日首发、11 月 7 日更新，HN 11 月 8 日约 689 分、424 评论）说明他为什么把主力 coding harness 从 Claude Code 换成开源的 Pi（earendil-works/pi，约 12 万星，自带统一 LLM API、agent 循环、TUI 和 coding agent CLI）。他的不满包括：长期不支持 AGENTS.md，要在 CLAUDE.md 之间复制或软链；VS Code 里同一时间只有一个会话能接收编辑器选区，这个 bug 从 2025 年 12 月报到现在；GUI 扩展里一半斜杠命令不能用，多个子 agent 输出按时间混在主线程里；今年 Claude Code 已发 244 个版本，超过 3/4 改了系统提示或工具描述，会改变模型行为、和仓库约定打架；默认 Bash 工具描述将近 3000 token，大半是 git 和开 PR 的说明。换到 Pi 后，他用约 20 分钟写了一个扩展，解决了多标签页接收选区的问题。

    为什么值得关注

    这条把「harness 本身就是上下文」讲得很具体：系统提示和工具描述的每一次改动都在改你的 agent 行为，而你不控制它。评论区的反方也值得看：用 Anthropic 订阅接第三方 harness 有违反服务条款、被封号的风险；Pi 不内置拦截危险操作的 auto 模式，第三方扩展也没人审。

    工作中怎么用

    评估团队用哪个 coding harness 时，把「系统提示和工具描述多久变一次、能不能锁版本、默认工具描述占多少 token」列进对比表。想试 Pi 这类开源 harness，用 API key 或允许第三方客户端的订阅，别拿 Claude 订阅硬接；并自己补上危险命令拦截和沙箱，不要因为极简就裸跑。

  3. 事件

    Mads Thines（在 Dash0 做 OpenTelemetry，也是开源 LoreKit 的作者）11 月 7 日发文，HN 11 月 8 日约 171 分、102 评论。他对比了九类记忆：指令文件（AGENTS.md、CLAUDE.md、Cursor .mdc）由人编辑、从不遗忘；Anthropic memory tool 由模型在 /memories 下写文件；GitHub Copilot Memory 存带代码引用的事实，28 天没用就删；Letta core memory 是带字符上限、常驻上下文的块；Mem0 由服务从消息里抽事实；LangGraph BaseStore 只有 put(namespace, key, value)，TTL 读到时续期；MCP 参考记忆服务器是实体/关系/观察的知识图谱；Graphiti/Zep 在图的边上记事实、按两条时间线失效而不是删除。已有的 Portable Memory（.mem 包、墓碑、签名）、Open Memory Protocol（4 月草案）、Cognee COGX 主要解决「把一个人的记忆从 A 搬到 B」，没解决 CI、编辑器 agent、审查机器人同时读写同一仓库的「实时寻址」。他给出一个示例记录：frontmatter 里有 address（如 repo 级）、key、id、kind、written_by（人 / agent / 抽取服务）、lifecycle、attributes（vcs.*、ci.*），正文是 Markdown；再配上统一的命名约定、通过 MCP 暴露的 write/read/list/search/archive 契约，以及用一致性测试代替参考实现。

    为什么值得关注

    昨天刚报过 Anthropic 讲 agent 记忆该记什么，这篇补上另一面：记下来的东西该长什么样、多个工具怎么共享。几个关键分歧（谁写的、何时失效、要不要指向依赖的代码）正是自建记忆层最容易拍脑袋的地方；文中也直说共享记忆就是提示注入的新通道。

    工作中怎么用

    自建 agent 记忆或上下文库时，至少给每条记录加上作用域地址、稳定 key（第二次写是更新还是新增）、写入者类型和过期策略这四个字段，并记录它依赖的代码路径或提交，方便判断是否过期。多个 agent 共享记忆时，按写入者区分信任级别，必要时签名。

  4. 事件

    openai/openai-agents-python 在 11 月 8 日（北京时间下午）发布 v0.24.0-alpha.7。新增：SessionStore、SQLiteSessionStore、CustomStorage 把根会话历史和 Python 工具结果存在应用自己的存储里，并能报出「不确定是否执行过」的工具调用供显式核对，不会自动重放；Agent.transform_context 改变送给模型的输入而不改存储的历史，before_compact 和选定条目保留控制压缩，before_complete 可以接受、继续或终止一个拟定答案；RunBudget 按请求数、token 或估算成本限制根运行；Session 可以列出、读取 MCP resources、resource templates 和 prompts，读到的内容不会自动进上下文；新增原生 A2A 客户端/服务端适配器、Environment.local() 本地执行，以及只搜不执行的 project_glob / project_grep。升级要点：新建 Environment 默认 write_policy="strict"；MCP approval_mode 的 auto 改名 native、approve 改名 preapproved，旧值直接报错；ElicitationRequest 拆成 FormRequest 和 UrlRequest；gpt-6-astra、gpt-6.1-sol、gpt-5.6-sol 的默认推理强度从 low 改为 medium。

    为什么值得关注

    这几项正好是生产 agent 最常自己造轮子的地方：会话落自家库、压缩时保住关键上下文、在答案发出前加一道审查、按成本封顶、工具副作用不确定时不盲目重放。默认推理强度悄悄升到 medium 会直接影响成本和延迟。

    工作中怎么用

    如果在用 alpha 线，升级前搜一遍 approval_mode 和 before_step 回调，显式写上 reasoning_effort。即使不用这个 SDK，也可以照它的设计给自家 agent 加三样：会话存储里标记「结果未知」的工具调用并要求人工或程序核对；压缩前钩子保留关键条目；按 token 或成本的运行预算。

  5. 事件

    synchopate/llama-modchip（Apache 2.0，10 月 29 日建仓，v2.4.0，HN 11 月 8 日约 350 分、145 评论）是针对稀疏 MoE 模型的 CPU 推理补丁集。README 给出的数字：常规 UD-IQ1_S 版 DeepSeek-V4-Flash（284.33B 总参数、13.17B 激活）占 76.87 GiB，超过 64GB Linux 机器约 62.5 GiB 可用内存；它转码到 56.56 GiB，连同 256K KV 缓存峰值 VmRSS 57.61–58.9 GiB，不用 swap。16 核 Zen 5 上 284B 预填充 44.36 tok/s、生成 9.1–14.7 tok/s；30B MoE（如 Nemotron-3.5-30B-A3B，14.35 GiB）CPU 生成 25–111.6 tok/s。手段包括 AVX-512 多级缓存分块（预填充 +77%、生成 +53%）、非临时 MoE 流式读取避免冷专家挤掉 L3 里的 KV，以及 1.64 MB 的 n-gram 自推测草稿器和从 /dev/shm 13.1 ms 恢复 KV 槽位。

    为什么值得关注

    本地跑大模型给 coding agent 用，一直卡在内存和长上下文；这个项目把「64GB 台式机跑 284B、256K 上下文」做成可复现的配置，还专门针对 agent 会话的 KV 快速恢复。数字目前都来自作者自己的 README 和论文，社区排行榜刚开始收集。

    工作中怎么用

    有不能把代码发到外部 API 的场景（比如支付核心代码），可以在一台 64GB 机器上试 30B MoE 档位做本地 coding agent 后端，先用自己的仓库测实际生成速度和质量；284B 档位 9–15 tok/s 更适合离线批量审查而不是交互。

  6. 事件

    11 月 8 日两篇文章同时上了 HN。芬兰开发者 Kristian Polso 的《Why I will not be using LLMs in my coding》（约 105 分、217 评论）说他做了 10 年机器学习，但决定在工作中完全不用 LLM 和 agent：长时间使用后感到迷糊；Claude 生成的代码看着完整、带一堆注释和测试，细看常常绕远路，本来几行 schema 改动和迁移就能解决；全由 agent 写的代码终将没人看得懂；还有能耗、对美国公司的依赖和 GDPR / CLOUD Act 问题。Sergey Kuhne 的《How I'm fighting the AI Brain Fry》（约 133 分、120 评论）给出另一条路：每个工单是仓库里的 Markdown 文件，看板状态提交进 git；agent 按轮次调研、只构建人标过「可以做」的工单、跑测试和浏览器检查，敏感代码走分支并先问，从不部署生产；需要他判断的事由脚本汇总成一个按优先级排好的「待裁决」列表，用一个从 git 重建的 Claude artifact 页面阅读，裁决写回 git。关键是一次只拿一件、做完就放回队列，不在脑子里挂着。

    为什么值得关注

    并行跑多个 agent 会话把人的注意力榨干，这在团队里已经很普遍。一篇代表反对派最完整的理由清单，一篇给出可以照抄的工作流，放在一起看能帮你判断该改的是工具还是流程。

    工作中怎么用

    团队推多 agent 并行时，试 Kuhne 的做法：任务状态全进仓库，agent 只做标记过的工单，所有需要人决定的事集中到一个列表，逐条关闭。拿 Polso 的清单做内部风险评审，尤其是「看着完整但走远路」的代码，审查时专门问一句「有没有更小的改法」。
