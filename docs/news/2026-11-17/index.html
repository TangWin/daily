  1. 事件

    Qwen 团队 11/16 发布 Qwen4 系列的第一个模型 Qwen4-Max：稀疏 MoE，总参数 2.4T，每 token 激活 71B（比 Qwen3.8-Max 少 25%），支持文本、图像、视频和 1M 上下文，只通过 QwenCloud API 提供，不开放权重。官方称 High 推理模式下 token 用量少 35%、单任务成本降约 60%，较小的 Qwen4 开源权重模型「很快」发布。官方公布的 16 项基准里，它在 DeepSWE v1.1（75.7，Opus 5.5 为 74.2）、Agents' Last Exam v1.1（46.7）等 4 项拿第一；但 Terminal-Bench 4.0 只有 48.5（Kimi K3.1 为 67.2、Opus 5.5 为 59.6），ProgramBench 只有 31.5（Opus 5.5 为 65.0）。OpenRouter 上的价格是输入 $1.50 / 输出 $4.50 每百万 token。CodeRouter 当天用 175 道单文件 Python 题实测：允许重试一次时通过率 96.0%（Sonnet 5.5 是 100%），总成本和 Sonnet 差不多，每题中位耗时 11.3 秒，Claude 系列是 4–5.5 秒。

    为什么值得关注

    这是中国厂商最强的闭源 agent 模型，但成绩很不均衡：SWE 类修 bug 任务很强，终端操作和从零写程序明显弱。HN 评论区的焦点有两个：开源模型和闭源模型的差距是不是在拉大（这次干脆不开权重），以及 Artificial Analysis 上它得 43 分、平均成本 $3.27，而 GPT-6.1 Sol（medium）得 46 分、只要 $0.36，性价比并不突出。

    工作中怎么用

    1）别只看厂商榜单。拿自己仓库里的真实任务分三类评估：修 bug（SWE 类）、跑终端（Terminal 类）、新写模块，Qwen4-Max 在这三类上的表现很可能差别很大；2）有数据合规要求、需要国内云的团队，可以先把它接到 CodeRouter / OpenRouter 这类路由层做 A/B，只把修 bug 类任务分给它；3）关注随后发布的 Qwen4 小尺寸开源权重，它们更适合做本地 Java 代码补全、代码审查。

  2. 事件

    美东时间 11/16 上午 11:30 左右开始，大量用户反映 Chase 网银和转账异常，Bank of America、Wells Fargo、US Bank 的报障也跟着上涨。JPMorgan 的声明是：问题出在「本地（on-premise）硬件系统中的一个软件 bug」，没有证据表明与网络攻击有关，客户仍能访问账户和资金，只是部分交易比平时慢；其他银行只在和 Chase 有交易往来时受影响，「不是系统性问题」。US Bank 说自身系统没受影响，但客户和其他银行之间的 Zelle 转账可能延迟；Zelle 说自己的网络运行正常。美联储的 ACH 等系统全程正常。当晚报障数量回落。这件事发生在 Microsoft 邮件大宕机、FAA 全美停飞之后不到一周。

    为什么值得关注

    这是今天和支付系统最相关的事件。最大的银行一出故障，Zelle 这类多方清算网络上所有对手方都会被拖慢，「不是系统性问题」的说法和用户看到的情况并不一致。HN 评论区吵得最多的是：最近这一连串大故障，是否和 AI 写代码、QA 被砍有关。也有人反驳说，同时出问题更可能是交易对手方被连带，而不是几家银行同一天上线了烂代码。另有评论指出 Downdetector 的数据本身会因为恐慌而虚高。

    工作中怎么用

    1）做支付对接的系统，把「对手方银行慢」当成常规故障来设计：设置超时并区分「已受理未确认」状态，幂等重试加对账补偿，不要把慢响应直接判成失败后重复扣款；2）按对手方（银行、Zelle、卡组织）分别建延迟和成功率看板，能比 Downdetector 更早发现上游故障；3）事故复盘时，把「这次变更是不是 agent 写的、有没有人审过」也记下来，用数据回应「AI 写代码导致故障」这类争论。

  3. 事件

    Glow Labs 本月初披露、Threat Frontier 11/16 详细报道的「MCPhantom」研究发现：Claude Code、Cursor、Codex CLI 等 agent 在帮开发者配置 MCP 时，经常装上 @modelcontextprotocol 名下已经归档的参考服务器。在 agent 装了这类已弃用服务器的会话里，98% 是 agent 按训练数据里的记忆自己选的，用户并没有指定。涉及的 12 个归档包自 2025-07-10 以来累计下载 17,352,267 次，下载量最大的是 server-github（526 万）、server-postgres（431 万）和 server-slack（320 万）。Glow 报告了 4 个高危漏洞，目前只公开了一个：server-puppeteer 中，网页里的 prompt 注入可以让 agent 启动任意进程，而不是只开浏览器。这些漏洞都没有 CVE；维护方答复「仓库已不再维护，不会发布修复」，报告也被以超出范围为由关闭。

    为什么值得关注

    这是一种新的供应链风险：不是有人投毒，而是 agent 的知识停留在过去，自动选中了已经没人维护的包。基于 CVE 的扫描器完全发现不了。另外要注意：同一个 scope 下还有 7 个没有归档的参考服务器，只按 scope 屏蔽会误伤，必须按包名匹配。

    工作中怎么用

    1）今天就扫一遍团队机器和仓库里的 MCP 配置以及 npx 命令，查有没有这 12 个包名，换成服务方官方维护的版本（比如 GitHub 官方 MCP），没有官方版本的就直接移除；2）每个服务只批准一个 MCP 服务器并写进团队模板，防止 agent 在新项目里又装回它记得的旧包；3）在 Claude Code 等 harness 的 PreToolUse hook 里拦截安装已弃用 npm 包的命令，并把 npm 弃用状态加入 MCP 服务器的准入检查。

  4. 事件

    modelcontextprotocol/java-sdk 11/16 发布 v2.2.0（此前有 M1、M2 两个里程碑版本）。服务端：完全无会话，每个请求独立处理；同一套代码既能同步也能异步，由 transport 决定是否把阻塞代码放到别的线程；tools、resources、prompts 从你自己实现的 repository 里取，所以按租户过滤、分页的工具目录很容易做；handler 可以自己选择返回普通 JSON 还是 SSE 流；通过了 2026-07-28 服务端所有必选一致性测试。客户端：没有 initialize 握手，一个 client 对应一个用户，多个 client 可以共用一个 transport，调用写法如 client.tool("create_issue").arguments(args).call()；支持 _meta、版本重协商、多轮 input_required（表单和 URL elicitation）、Mcp-* 请求头、subscriptions/listen、server/discover，以及按 ttlMs 缓存工具列表；已通过非鉴权部分的客户端一致性测试，sampling、roots、logging 暂不支持。按 SEP-2577，发起 roots、sampling、logging 的 API 标为弃用。破坏性变更：McpTransportContext 不再按内容比较 equals/hashCode。modern API 在 3.0 之前的小版本里还可能变化。

    为什么值得关注

    Java 团队对接新版 MCP 的主要障碍解决了。无会话意味着 MCP 服务器可以像普通无状态 REST 服务一样放在负载均衡后面横向扩容，不需要粘性会话，这对支付这类多实例部署的后端很重要。按租户返回工具目录的 repository 接口，也正好可以用来做最小权限。

    工作中怎么用

    1）新建的 Java MCP 服务直接用 io.modelcontextprotocol.modern.server.McpServer，旧服务先不动，legacy 和 modern 可以并存；2）在 repository 层按调用方的租户或角色过滤工具列表，例如支付后台只给客服 agent 暴露查询类工具；3）升级前先搜一下代码里有没有依赖 McpTransportContext 的 equals 或把它当 Map key 的地方；4）用 Spring AI 2.1 的团队留意它对 modern 协议的对接进度（RC2 已支持服务端）。

  5. 事件

    开发者 Xusheng Li 让 AI 帮忙翻 Windows 二进制，在 MissionControlAggregator.dll 里找到一串可执行文件名：CLI agent 槽位匹配 copilot.exe、claude.exe、codex.exe、agy.exe（WSL 里也会匹配不带 .exe 的同名程序），桌面 agent 槽位匹配 github.exe、claude.exe、codex.exe、cursor.exe、antigravity.exe，另外还统计 node、python、dotnet、gcc、javac、code.exe 等开发工具。对应的功能开关叫 CLICodingAgentUsage。它不自己扫描进程，而是订阅系统已有的 ETW 事件，大约每天生成一次 Segments.SubCohorts 报告。作者把 cmd.exe 改名为 codex.exe 运行，Codex 对应的位就被置位，报告随后出现在 DiagTrack 的上传队列里。这份报告属于「可选诊断数据」，作者在美区全新安装的 Windows 11 上验证，这一项默认开启。报告只记录用了哪些工具，没有 prompt，也没有源码。

    为什么值得关注

    这是一份可以复现的逆向证据：操作系统厂商在统计开发者用的是哪家 coding agent，这本身就是有竞争价值的数据。对企业来说，开发终端的遥测策略原本只管业务数据，现在也得把「工具使用画像」算进去。

    工作中怎么用

    1）公司的 Windows 开发机通过组策略关闭可选诊断数据（AllowTelemetry 降到必需级别），个人机器在 设置 → 隐私和安全性 → 诊断和反馈 里关掉；2）想自查的话，看 C:\ProgramData\Microsoft\Diagnosis\AggregatorStorage 下有没有 MissionControlAggregator 的状态文件；3）在做 agent 准入或合规评估时，把操作系统层的遥测也列进检查清单。

  6. 事件

    Coral 的联合创始人在 Show HN 介绍：Coral 是位于 agent 和企业系统之间的自托管网关。agent 不逐个调用工具，而是写一小段 TypeScript 程序来调用；任务跑通后，这段程序可以存成自定义工具，下次在搜索工具时会和 Datadog、Slack 等标准工具一起出现，团队之间也能共享。每段程序在没有网络和凭证的 V8 isolate 里执行，Coral 对每次调用先按工作区策略检查，通过后才附上凭证转发给服务方；也可以配置成使用调用者本人的账号，这样同事共享工具时不用共享 API token。它的出发点是做 AI SRE：agent 排查故障需要很宽的权限、消耗大量 token，下次还得从头再来。官方 demo 里，同一个任务第二天直接调用存好的工具，token 少 35%、速度快 31%。有桌面版，也能用 Docker Compose 或 Kubernetes 部署共享服务器，需要 OIDC 身份提供方，开源版不限用户、agent 数量和调用量。

    为什么值得关注

    它的核心观点是：大多数 MCP 网关只能决定 agent 看得到哪些工具，要么全给要么不给；而自定义工具本身是代码，可以把业务规则写进去，例如 closeStaleTicket 只改一个字段，而且只对 30 天没有动静的工单生效。这比单纯给工具加 Allow/Block 精细得多。这和 Claude Code 的 Code Mode、Cloudflare 的 code mode 是同一个方向，但多了把经验固化成工具和团队治理这两层。

    工作中怎么用

    1）找一个重复性高、权限敏感的流程试点（比如每天汇总未审 PR、按规则关闭过期工单），对比直接调用 MCP 和使用存好的工具在 token 和耗时上的差别；2）借鉴它的权限模型：在支付后台这类场景里，不要直接把 update_refund 这种宽权限工具暴露给 agent，而是封装成 refundUnder(amount, orderAge) 这样带业务约束的窄工具；3）评估时重点看它的审批记录（谁批准了哪次调用）能不能接进现有的审计系统。

  7. 事件

    Anomaly（OpenCode 背后的公司）发布 Browse：由一个 MCP 服务器和一个 Chromium 扩展组成（MIT 协议），支持 Chrome、Edge、Brave、Arc 等浏览器，暂不支持 Firefox。agent 在折叠的后台标签组里工作，可以读取页面、点击、输入、截图、录制标签页和网络流量；遇到登录、2FA 或付款时，把标签页交给用户处理，用户点 Continue 后 agent 接着做。用户也可以通过工具栏按钮把自己正在用的某个标签页借给 agent，并能限定 agent 只访问指定的站点。

    为什么值得关注

    直接用用户自己的登录状态、不需要配置任何 key，非常方便，但这正是 lethal trifecta（私有数据 + 不可信内容 + 对外通道）的典型组合。HN 评论有人批评 OpenCode 发布太频繁、不重视安全，也有人指出 Playwright MCP、Chrome DevTools MCP 已经能做类似的事。值得借鉴的是它在付款这一步强制交还给人的设计：这和 ChatGPT Wallet 每笔付款都要人工确认是同一个思路。

    工作中怎么用

    1）如果要试，单独建一个浏览器 profile 给 agent 用，不要用存着公司 SSO 和支付后台登录的主 profile，并且只把允许访问的站点设成测试环境；2）自己做 agent 浏览器自动化时，借鉴「遇到登录、2FA、付款就交还给人」的设计，在支付和下单流程里明确设置人工确认点；3）和 Playwright MCP、Chrome DevTools MCP 做个对比，按隔离程度、能否只授权单个标签页来选型。

  8. 事件

    Claude Code v2.1.326（北京时间 11/17 06:11 发布）：开启 agent teams 时也能用 Code Mode；--allowedTools、--disallowedTools、--tools 里有写得不完整的规则时，启动时会给出警告；管理员在会话中途加入 managed-mcp.json 导致 MCP 停止加载时，会说明原因；新增 OTEL_RESOURCE_INCLUDE_HOST 选项。修复的问题包括：find -delete、cat a > b、sort -o 这类删除或覆盖文件的 Bash 命令在记录里被归为「搜索」或「读取」；在 /permissions 里加的规则在设置文件写入失败时看起来已保存，现在会警告并给出文件名；一个 MCP headersHelper 失败会导致其他会话也加载不到该服务器；嵌套几千层的设置文件会导致崩溃（现在超过 64 层的值会被丢弃并警告）；在已信任父目录下的信任提示里，按上键再回车会被当成「是」。OpenAI Agents SDK（Python）v0.24.0-alpha.8（11/16）：Python 工具执行前可以审核参数，批准或拒绝，并在整个 Session 内记住这个决定（FunctionToolApprovalRequest/Decision）；run_input_policy_before_approval=True 时，输入策略会在审批判断之前先跑一遍；tool-search 和托管 MCP 的审批决定都可以通过 ModelOutputItemCompleted 观察到；从带预算的检查点恢复时会保留已用的请求和 token 预算；可以接入自己的模型客户端（LiteLLM 等）。

    为什么值得关注

    两边的改动方向一致：不只是「能不能调用」，还要保证人看到的操作和实际执行的一致（覆盖文件不能显示成读取），保证权限配置真的生效（写入失败不能静默），审批结果要可观测、可恢复。这些看起来都是小 bug，但每一个都可能让「人在环」的审批形同虚设。

    工作中怎么用

    1）升级 Claude Code 后检查启动时有没有规则格式警告，顺便清理团队 settings 里写得不完整的 allow/deny 规则；2）在 /status 里确认遥测和功能开关的真实状态；3）用 Agents SDK 做支付类 agent 的，把退款、转账类工具改成走 FunctionToolApprovalRequest，并打开 run_input_policy_before_approval，让金额上限这类校验在人工审批之前先跑；4）把审批决定接进日志，事后能查到谁批准了哪次调用、参数是什么。

  9. 事件

    Jimmy Breck-McKye 的文章把 2026 年接连出现的故障放在一起看：Microsoft 两天的全球宕机、FAA 全美停飞、PHP2Shell RCE、npm 的 Shai Hulud 投毒、eMudhra 证书私钥过弱。他认为这些事件的直接原因各不相同，但形态相似：系统由大量低质量部件组成，没有人能看清全貌。AI 既是原因（生成复杂度太快，攻击者用 AI 几个小时就能找到复杂漏洞），也是症状。他最担心的是公司失去「组织认知」，即作为一个整体去理解和应对系统的能力。同一天的 Ask HN「如果 AI 工具这么好，为什么你的 bug 积压还没清空？」里，高赞回答说 agent 修 bug 大多只是针对症状打补丁，很少提出需要权衡的根本修复；也有工程经理说自己团队的积压确实已经清空，瓶颈变成了代码审查。

    为什么值得关注

    这类讨论每周都有，但这次刚好赶上 Microsoft、FAA、JPMorgan 连续出事，引起的共鸣明显更大。最有用的是评论区的一个反面观点：AI 很擅长照着模式写代码、写测试，但大多数团队不擅长把模式、规则和启发式写成文档，而这恰恰是 Context Engineering 要解决的问题。

    工作中怎么用

    1）给 coding agent 配一份写清楚的架构约定和不变量文档（比如支付里的幂等键、金额只用整数分、状态机允许的转移），agent 和人都按它来审；2）修 bug 时要求 agent 先写出根因分析和可选方案的取舍，再动代码，不接受只针对症状的补丁；3）把代码审查当成主要瓶颈来管理：度量 PR 等待审查的时长，把机械性检查交给 CI 和 agent，人只看设计和风险。
