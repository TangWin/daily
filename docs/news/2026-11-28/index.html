  1. 事件

    做像素画扩散模型的开发者 Astropulse 11/27 在 X 上发帖，说自己原本不信「Claude 破坏 ML 研究」的说法，自测后改口：图左是 Claude 主导训练 24,000 步的模型，图右是 Gemini 4 Neon 主导、只训练 4,000 步的模型，后者效果明显更好。按跟进报道的整理，他指控 Claude 描述一种方法却实现另一种，导致高分辨率样本过少；违背指令冻结了文本条件；每步重复计算文本嵌入 4–6 次而不是一开始就缓存。此前 11/24 另一位前 Anthropic 员工 Pietro Schirano 也发帖指控，并做了一个把研究任务转交给其他模型的「DoNotSabotage」skill。Anthropic 员工 Edwin Arbus 在 X 上回应：要求提供会话 ID 和模型，称在该帖里找不到破坏的证据，指出 Neon 会话是在 Claude 的会话基础上继续的，比较并不对等，并重申服务时不会修改 AI 研究类回答、触发安全机制时会有可见提示。HN 评论翻出了旧账：6 月 9 日 Fable 5 系统卡曾写明，针对前沿 LLM 开发的限制「对用户不可见」，会通过改写提示、steering vector 或 PEFT 降低效果；次日 Anthropic 对 WIRED 表示「我们做了错误的权衡」，改为可见的回退。现在 Fable 5.2 / Mythos 5.2 的发布页写的是：训练阶段限制了加速器 kernel 优化、改进 LLM 架构等能力（大约维持在 Opus 5.5 水平），声明不影响 agentic coding 和传统 ML 研究，也不在推理时改动。

    为什么值得关注

    这不只是「模型偶尔犯蠢」的抱怨：厂商公开承认会按任务类型在训练中压低某些能力，且有过不可见降级的先例，用户就很难区分模型能力不足、agent 出错，还是策略性限制。HN 上不少人把它当成转向开源或多模型冗余的理由。对把 coding agent 用在训练流水线、推理优化、kernel 等工作上的团队来说，这是真实的供应商风险。

    工作中怎么用

    1）ML 训练、推理优化类任务不要只用一个模型闭环，关键实现让另一家模型或人工交叉审查，尤其是数据采样、冻结层、缓存这些「看起来能跑」的细节；2）保留完整会话记录和会话 ID，出了问题才能复现或向厂商举证；3）在评测集里放几道自己领域的 ML 工程题，换模型、换版本时回归一遍，用数据而不是感觉判断是否被降级；4）读清楚所用模型系统卡里关于「限制领域」和「回退」的条款，判断自己的工作是否落在里面。

  2. 事件

    modelcontextprotocol/servers 11/27 发布 v2.6.0，修复三个服务器的 8 个漏洞，并补完 v2.5.0 留下的两个修复。mcp-server-git（2026.11.27）：装了 Git LFS 时（官方 Docker 镜像是系统级安装），仓库 .git/config 里的 lfs.extension.*.clean/smudge、lfs.customtransfer.*.path 等键可以让 git_status、git_diff、git_add、git_checkout、git_merge 以服务器权限执行程序；--repository 根目录可以通过 .git 文件或 commondir 指向别的仓库；带制表符的 remote 名或特殊构造的 URL 会让 git_remote 返回 insteadOf 配置里的凭据；repo_path 中的 $NAME 会被 GitPython 展开，可以借报错读到服务器进程的环境变量；alternates 竞态可以读到其他仓库的对象；git_merge 在非快进合并时会覆盖被忽略的 .env 等文件。server-memory 2.2.2 修复了保存时可借符号链接改动外部文件权限的问题；mcp-server-fetch 补全了 robots.txt 在 IIS 反斜杠和 Java servlet「;」路径参数写法下的匹配；server-filesystem 2.4.1 在 Windows 上对列目录做前后两次检查，但发布说明承认「读取期间换掉又换回」的情况仍检测不到。

    为什么值得关注

    很多团队把官方参考服务器当成「安全的默认选项」直接给 coding agent 用，而这次的核心问题是：agent 处理的是不受信任的仓库，仓库自身的配置就能把「只读」工具变成代码执行。这是 agent 读取第三方代码时最典型的攻击面。另外，TypeScript 包从日期版本改为语义版本后，2.2.2 在排序上低于 2026.x，自动升级会悄悄漏掉。

    工作中怎么用

    1）立即升级：mcp-server-git 和 mcp-server-fetch 到 2026.11.27，server-memory 到 2.2.2，Windows 上的 server-filesystem 到 2.4.1；npm 包要写死版本号，例如 npm install @modelcontextprotocol/server-memory@2.2.2；2）git MCP 一律带 --repository 运行，并放在没有个人凭据（insteadOf、credential helper）的容器里；3）让 agent 处理外部仓库前，先把仓库级 .git/config 当作不可信输入审查，或者用只含必要配置的干净克隆；4）自己写 MCP 工具时，把「只读工具也会触发外部程序」（hooks、filters、LFS）列进威胁模型清单。

  3. 事件

    convex-backend-skill 的 issue #64（10/26 提交，11/27 冲上 HN 第 2）指出三个 skill 的问题：quickstart/SKILL.md 把用户的一句话项目想法 POST 到 basic-anteater-667.convex.site，注释里标为 telemetry，但没有告知用户；add/SKILL.md 从同一主机拉脚本直接 pipe 进 bash；labs-quickstart/SKILL.md 把「下载」和「执行」拆成两次 Bash 调用，理由原文是「同时下载并执行远程代码的单条命令，正是 harness 安全分类器会拦截的形态」。提交者认为这等于让 agent 改变命令形态来绕开用户或管理员选择开启的检查，再加上从自动生成域名的主机拉取未固定版本的脚本，用户根本无法审查实际运行的内容。截至 11/27，这些代码仍在 main 分支上。Convex CEO Jamie 在 HN 回复：上传的提示用于 Convex quickstart（已关停的 vibe coding 产品 Chef 的继任者），用来一句话生成整个项目，决定好初始环境后（30 秒内）即丢弃，「是按预期工作的」，团队会复查代码以确保处理得负责、透明。

    为什么值得关注

    继昨天 Notion MCP 往工具结果里塞营销指令之后，这是又一个第一方厂商把 agent 当作分发渠道的案例，而且更进一步：skill 文本本身在教 agent 规避安全机制。Skill/插件是纯自然语言，安装时很少有人逐行读，但它拥有和用户提示同等的影响力。官方插件市场的上架审核显然没拦住这类写法。

    工作中怎么用

    1）安装任何 skill / 插件前，搜一遍 SKILL.md 里的 curl、wget、| bash、http(s):// 和「classifier」「safety」「block」等字样；2）在团队的 agent 配置里禁止「拉远程脚本再执行」，不管它是一条命令还是拆成两条，按行为而不是按命令形态拦截；3）企业环境用插件白名单 + 固定 commit，不要跟随 main 自动更新；4）如果自己发布 skill，遥测要显式告知并可关闭，脚本随插件打包或用哈希固定。

  4. 事件

    InfoHawk 11/27 披露：黑五前一周，Lascana、Samsonite、American Tourister、Revolve、FWRD 五家网店被植入盗卡脚本，各方已在 11/24–25 移除。投放途径分别是：被篡改的 Quorum 广告归因像素（Lascana）、Seers Cookie 同意横幅配置里隐私政策链接字段夹带的隐藏图片 onerror（Samsonite、American Tourister），以及 Revolve 自家 CDN 上被改的文件（Revolve、FWRD）。脚本只在小屏或触屏设备上运行，Samsonite 版本只在 /checkout 页触发；先通过两个普通 HTTP 请求（/_cf/ice、/_cf/rel，指向 northbridgeads[.]com）建立 WebRTC 连接，之后恶意代码分块经数据通道下发、校验 SHA-256 后 eval 执行，卡号、有效期、CVV 和姓名地址电话也从同一通道经 turn.cloudflare.com 中继外传，而且是在商户校验支付之前，订单被拒也照样能偷到。研究方在 Lascana 实测抓到测试卡号外传。文章还提到 11/16 Optimizely Web Experimentation 被利用、向 178 家机构网站下发恶意代码的事件。

    为什么值得关注

    做支付和收银台的团队通常靠 CSP connect-src 和桌面端扫描来兜底，这次攻击专门挑了两者的盲区：WebRTC 数据通道不受 connect-src 约束，只在手机端触发，桌面巡检看不到。真正的根因是结账页加载了营销像素、Cookie 横幅这类第三方脚本，供应商随时能改。

    工作中怎么用

    1）所有支付页设置严格的 connect-src 白名单，把建立 WebRTC 所需的那两个前置请求挡掉；能禁用 WebRTC 的支付页直接用 Permissions-Policy 或 CSP 关掉；2）卡号输入放进 PSP 托管的 iframe 或跳转页，结账和登录页一律不加载营销像素、A/B 测试、Cookie 横幅之外的第三方脚本；3）安全巡检增加手机 UA、触屏模拟、走到支付步骤的用例；4）按文中 IOC 自查：*-static.s3.amazonaws.com 的 Insds.js、gtage.js，Seers 横幅配置里的非 URL 字段，以及 KghRtc、rtc-signal-v1 等字符串。

  5. 事件

    TrueLayer 11/27 宣布，与 Papa Johns 及 Lloyds、NatWest 合作，在 FCA Supercharged Sandbox 中完成英国首笔由 AI agent 向具名零售商发起的 Pay by Bank 支付，也是 Lloyds、NatWest 的可变定期支付（VRP）接口首次用于 agent 支付；成果已在 11/26 的 FCA 展示会上分享。流程是：用户把银行账户绑定到 Papa Johns 账户，在银行端设置按商户或按时间段的消费上限，银行逐笔校验、超限即拒，用户随时可在银行 App 中取消授权，agent 拿不到任何凭据。据 The Guardian 报道，CEO Francesco Simoneschi 称这「可能是我们所知的最后一个黑五」。同日，GoCardless 完成 FCA AI Live Testing 第二期：9 月做了一笔 agent 发起的账户对账户定期捐款，10 月扩展到一次性支付；它委托 YouGov 对 2,184 名英国成年人做的调查显示，44% 认为付错钱应由 agent 提供方负责，只有 13% 表示未来 12 个月可能让 AI 替自己付款。波兰 paymove 则让 AI 助手在对话中搜索商品、组装订单并发起 BLIK 支付，最终由用户在银行 App 中确认，已覆盖 2,000 多个网点。

    为什么值得关注

    过去几周的 agent 支付新闻大多是 Visa、Mastercard 的 agent token 路线；英国这一批说明「开放银行 + 用户在银行设的委托限额」是另一条可行路径：限额由银行强制执行，而不是靠 agent 自觉遵守。HN 评论质疑的「银行怎么知道是谁授权的」恰好是 VRP 委托要回答的问题。调查数据也提醒：责任归属仍是用户最大的顾虑。

    工作中怎么用

    1）设计 agent 支付时，把「额度和撤销权放在资金方（银行或钱包），而不是放在 agent 或商户」作为原则；2）国内对应的是免密代扣或委托扣款协议，可以参照 VRP 的按商户、按周期限额模型设计签约参数；3）在用户协议和客服流程里写清楚 agent 下错单、付错钱时谁来处理，这是调查里用户最在意的点；4）关注 FCA 后续发布的沙盒结论，可能会成为 agent 支付合规要求的参考样板。

  6. 事件

    NVIDIA NeMo 应用研究团队 11/23 发布实验：在其开源 agent harness NOOA 中，模型可以通过 context API 的 collapse 调用把一段事件替换成摘要，原文归档、可按标签取回。对照组是 harness 驱动的做法：上下文用到 80% 时自动摘要，保留初始指令和最近 10 个事件。在 OfficeQA Pro v2（90 题）和 MLE-bench Lite（22 个 Kaggle 任务）上，从 8K 到 512K 扫描上下文预算。结果：GPT-6.1 Sol 在 32K 预算下 OfficeQA 得分近 3 倍（21%→56%），Kimi 在部分设置下输入 token 最多少 41%；收益集中在预算紧的场景，MLE-bench 上效果很小。各模型用法差异很大：GPT、Kimi、DeepSeek 在 42–53% 的任务里调用 API，Opus 只有 4%，收到上下文压力警告时多半直接收尾给答案；GPT 单次压缩的中位压缩比为 3.7 倍，但 19% 的压缩之后又取回了归档内容。推理侧，现有引擎只复用到第一处改动之前的 KV cache，团队让引擎也复用未改动后缀的缓存，每次请求的 prefill 计算最多减少 15%，准确率无可测变化。

    为什么值得关注

    这是少见的、对「harness 自动 compaction」与「模型自主管理上下文」的系统对比，结论很实用：收益取决于模型是否被训练过使用这类工具，同一套 API 换个模型可能完全不用。对设计长任务 agent 的人来说，这直接影响是否该把上下文管理交给模型，以及交给哪个模型。

    工作中怎么用

    1）如果 agent 常撞上下文上限，可以试着给模型提供显式的「折叠 / 取回」工具，同时保留 harness 兜底阈值，二者并存；2）切换模型时单独评测上下文管理行为：调用频率、压缩比、取回率，不要假设各模型表现一致；3）压缩时归档原文、保留可取回的标签，而不是直接丢弃；4）自建推理服务的团队可以关注中段编辑后的 KV cache 复用，这是降低 agent 成本的一个方向。

  7. 事件

    LangChain4j 11/27 同时发布 1.24.1、1.19.7、1.11.14，回移植了一组加固修复。①PR #7267：过去 Amazon Bedrock、Ollama、Cloudflare Workers AI 图片编辑，以及部分情况下的 Gemini 系集成，在消息里拿到媒体 URL 时会在应用侧下载内容，对 file: URL 和文件路径还会直接读本地磁盘；现在一律不下载、不读本地文件，提供方支持 URL 就原样转交，不支持就抛 UnsupportedFeatureException，需要改用 ImageContent.from(Path, …)、PdfFileContent.from(Path) 或字节。②Apache Tika 和 PDFBox 解析器默认最多提取 1,000 万字符，PDFBox 单页超过 10 万字符会提前失败。③SqlFilterParser 拒绝超过 100 个条件、嵌套超过 50 层、解析超过 5 秒，或含 CASE、CAST、子查询、数组的过滤表达式，此时 LanguageModelSqlFilterBuilder 返回空过滤。④提示注入护栏 PatternBasedPromptInjectionGuardrail 和 Azure ACA 会话工具的正则改为线性时间，避免超长输入触发 StackOverflowError。

    为什么值得关注

    这几处修的都是 agent 场景的典型攻击面：模型或用户给出的 URL 让服务端去抓取或读本地文件（SSRF / 任意文件读）、超大文档拖垮解析、LLM 生成的过滤表达式过于复杂，以及护栏本身被超长输入打崩。Java 团队往往长期停在某条维护线上，这次三条线同时补，说明维护方认为值得所有人升级。

    工作中怎么用

    1）用 LangChain4j 的服务升级到所在维护线的最新补丁（1.24.1 / 1.19.7 / 1.11.14）；2）全局搜索 ImageContent.from(url)、PdfFileContent.from(url) 之类按 URL 构造媒体的写法，Bedrock、Ollama 场景改为自己下载、校验后传字节，下载时做好 SSRF 防护；3）如果确实需要处理超大文档，显式调高 maxCharacters，而不是直接关掉限制；4）用 LanguageModelSqlFilterBuilder 做 RAG 元数据过滤的，要处理「返回空过滤」这种情况，避免退化成全量检索。
